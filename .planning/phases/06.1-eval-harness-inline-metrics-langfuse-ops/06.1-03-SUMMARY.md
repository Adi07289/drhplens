# Phase 06.1 Plan 03: Langfuse Direct-API Trace Enrichment (EVAL-05) Summary

**Made agent tracing actually work via the direct client API (the CallbackHandler was silently no-op without langchain), attaching cost/latency/tool-call metadata + a failure-mode custom score from an 8-value taxonomy, with a test-pinned no-op fallback and mandatory flush().**

## Performance

- **Files created:** 2 (1 module + deferred-items log)

## Accomplishments
- `app/observability/trace_enrichment.py`: `emit_enriched_trace()` emits a real Langfuse trace via `lf.trace(name, metadata=..., tags=["eval-05"])` → `trace.score(name="failure_mode", value, comment)` → attaches cost/latency/tool-call-count metadata + an 80-char question preview.
- `FAILURE_MODES` taxonomy extends the 4 refusal reasons (`low_retrieval_score/unsupported_claim/banned_token/infrastructure_error`) with `retrieval_miss/cite_check_fail/judge_flag/crash`; `classify_failure_mode()` and `count_tool_calls()` are pure and deterministic from state.
- `agent/graph.py::invoke_with_tracing` wired to time wall-clock latency (`time.perf_counter`), count tool calls from `final_state`, emit the enriched trace, and `flush()`; a crash still emits a `crash`-classified trace then re-raises.
- No-op fallback hardened and test-pinned: with keys unset, `emit_enriched_trace`/`flush` construct **no client** and make **no HTTP call**. Verified live against Langfuse Cloud with `--run-langfuse` (the direct-API trace + `failure_mode` score attach).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Corrected a pre-existing test asserting a spike-disproven invariant**
- **Found during:** Task 3 (full-suite regression run).
- **Issue:** `test_langfuse_client_initialized_when_keys_present` asserted `type(handler).__name__ == "CallbackHandler"`. Spike 001 (this plan's foundation) proved `get_callback_handler()` silently returns `_NoOpCallbackHandler` when `langchain` is absent (the repo ships only `langchain_core`), so the assertion was false. It failed on the committed HEAD (reproduced with my changes stashed) — a pre-existing failure encoding the exact bug this plan routes around, in a file I own (`test_langfuse_trace.py` is in `files_modified`).
- **Fix:** Rewrote the test to assert the measured reality — the DIRECT client (`get_client`) is the real trace path, and the handler type is environment-robust (`CallbackHandler` only if `langchain` present, else `_NoOpCallbackHandler`).
- **Files modified:** tests/integration/test_langfuse_trace.py
- **Verification:** Test now passes; suite green apart from the unrelated live-Gemini timeout.
- **Committed in:** `124d845`

**2. [Rule 3 - Blocking] Gated the live-attach test on `--run-langfuse`, not just the env var**
- **Found during:** Task 3.
- **Issue:** The plan said to reuse the existing env-based `_langfuse_skip` marker, but langfuse v2 auto-loads `.env` on import, so `LANGFUSE_PUBLIC_KEY` is populated under pytest even without `--run-langfuse`. That defeated the skip marker — my new live test (and the pre-existing gated tests) ran and hit the network on the default path, violating the Task 3 acceptance criterion "skipped without --run-langfuse / off the default CI path."
- **Fix:** Gated the live attach on `request.config.getoption("--run-langfuse")` (skips by default; runs only with the flag). Documented the auto-load reason inline.
- **Files modified:** tests/integration/test_langfuse_trace.py
- **Verification:** Default run skips it (`1 skipped`); `--run-langfuse` runs it green against Cloud.
- **Committed in:** `124d845`
