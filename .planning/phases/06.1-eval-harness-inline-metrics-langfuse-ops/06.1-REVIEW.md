# Phase 6.1: Code Review Report

**Reviewed:** 2026-07-29
**Depth:** standard
**Files Reviewed:** 24
**Status:** issues_found

## Summary

Reviewed the eval-harness / inline-metrics / Langfuse-ops slice (metrics, runner, release
gate, inline UI surfaces, tracing, and their tests) for correctness, security, robustness,
and the load-bearing HONESTY INVARIANT.

**Honesty invariant — PASS.** Every domain guard I could verify holds:
- The committed `eval/reports/eval_summary.json` carries `faithfulness_deepeval = -1.0`
  (the "not measured" sentinel) at both aggregate and `per_ipo.swiggy_2024_11` level; no
  fabricated/verdict-styled number is surfaced.
- `ui/eval_inline.py` reads ONLY the committed JSON (`.is_file()` + try/except), imports
  no LLM/agent/judge module, and renders `-1.0` as `not measured` (never `0.00` / `-1.00`).
  Per-IPO line renders only when `per_ipo[drhp_id]` exists.
- The DeepEval judge is `gemini-3.5-flash` everywhere (no `gemini-2.5-flash` in live code),
  native `GeminiModel` on `GEMINI_API_KEY` (no OpenAI key), and uses `measure()` (reported),
  never `assert_test` on the gated path.
- The release gate hard-gates ONLY the deterministic `citation_accuracy` / `recall@10`;
  faithfulness is reported-only (proven by `test_eval_gate_does_not_block_on_low_faithfulness`).
- Langfuse uses the direct client API (`lf.trace/score/flush`) and no-ops before any client
  construction when keys are unset (proven by `test_emit_enriched_trace_noop_when_keys_missing`).
- Eval CSS (`.drhp-eval-*`, `.drhp-eval-live`) is neutral mono — no red/green, no badge.

No Critical/Blocker defects were proven. The findings below are correctness-on-the-error-path,
release-gate-integrity, deployment-sync, and maintainability issues.

## Warnings

### WR-01: Legacy `run_eval` crashes with KeyError whenever any gold entry crashes

**File:** `scripts/run_eval.py:216-217` (also `255`)
**Issue:** The crash branch appends a result dict lacking the `refusal_expected` /
`citation_accuracy` keys:
```python
results.append({"qid": qid, "category": category, "status": "crashed", "error": str(exc)[:200]})
```
The aggregation then accesses those keys unconditionally over ALL results:
```python
grounded_results = [r for r in results if not r["refusal_expected"] and ...]  # KeyError on crashed rows
```
Python evaluates `r["refusal_expected"]` before the `"citation_accuracy" in r` guard, so a
single crashed question aborts the entire report with `KeyError` — exactly when a crash most
needs to be recorded. Line 255 (`r["citation_accuracy"]` in the per-entry table loop) has the
same defect. Only affects the `--legacy` path (the release gate uses `run_rag_eval` /
`compute_numeric_faithfulness`), so it is not on the shipped gate path, but it is a real
unhandled crash in a reviewed file.
**Fix:** Give the crashed row the same shape as other rows, or guard with `.get()`:
```python
results.append({"qid": qid, "category": category, "status": "crashed",
                "error": str(exc)[:200], "refusal_expected": False,
                "citation_accuracy": None, "answer_coverage": None,
                "ragas_faithfulness": None, "recall_at_5": None})
```
and change the filter to `if not r.get("refusal_expected") and r.get("citation_accuracy") is not None`.

### WR-02: Gated citation/recall metrics can be inflated by empty/malformed spans

**File:** `eval/metrics/citation.py:24-37`, `eval/metrics/recall.py:32-45`
**Issue:** Two behaviors combine to silently raise the value of a HARD-GATED metric:
1. Empty `expected_sources` returns `1.0` vacuously. In `run_rag_eval`, `expected_sources =
   entry.get("expected_sources", [])`, so any grounded gold question missing its spans
   contributes a perfect `1.0` to the aggregate `citation_accuracy`/`recall`, diluting the
   signal upward toward the 0.95 gate and masking genuine attribution regressions
   (contradicts CLAUDE.md: "citation-accuracy regression is a hard CI failure").
2. Asymmetric span defaults: expected uses `page_start=0` / `page_end=9999`, chunks use
   `page_start=0` / `page_end=0`. A malformed expected source (missing both keys → `[0, 9999]`)
   overlaps essentially ANY chunk → false hit → inflated pass. A chunk with `page_start` set
   but `page_end` missing (→ `end=0`) conversely never matches → false miss.
**Fix:** For the gated metric, treat a grounded question with empty `expected_sources` as
uncounted (skip) rather than a vacuous `1.0`; and default missing chunk `page_end` to
`page_start` (or `inf`) rather than `0`, and reject expected sources missing both keys.

### WR-03: `requirements.txt` is materially out of sync with `pyproject.toml`

**File:** `requirements.txt:1-57` vs `pyproject.toml:13-85`
**Issue:** The header states "Keep in sync with pyproject.toml … HF Spaces reads this file
directly," yet requirements.txt omits many runtime dependencies present in pyproject:
`google-genai`, `fastembed`, `deepeval` (this phase's faithfulness judge), `ragas`, and the
entire Phase 4/5 runtime set (`yfinance`, `requests-cache`, `jugaad-data`, `xgboost`, `mapie`,
`scikit-learn`, `mlflow`, `matplotlib`, `shap`, `nse`). If HF Spaces installs solely from
requirements.txt, the deployed snapshot/forecast/peer/GMP pages and the eval runner would fail
to import their deps. (`google-genai` may resolve transitively via
`llama-index-llms-google-genai`, softening the risk — but the manifest contract is still broken.)
**Fix:** Regenerate requirements.txt from pyproject's `[project.dependencies]` (or install from
pyproject on HF), and add a CI check that the two stay in sync.

### WR-04: Judge-model provenance is a hardcoded string that can drift from the real judge

**File:** `scripts/run_eval.py:499`
**Issue:** `run_rag_eval` writes `judge_model="gemini-3.5-flash"` as a literal into the
committed `eval_summary.json`, independent of the actual judge id in
`eval/metrics/faithfulness_deepeval.py:63` (`GeminiModel(model="gemini-3.5-flash", ...)`).
The same id also lives in `agent/policies.py:76`. If the judge model is bumped in one place,
the committed provenance (and the UI's "judge {model}" clause + the schema's `_named_judge`
honesty guard) silently lies about which model produced the figures.
**Fix:** Source the provenance from a single constant, e.g. export
`JUDGE_MODEL = "gemini-3.5-flash"` from `eval.metrics.faithfulness_deepeval` and reference it in
`run_rag_eval` instead of re-typing the literal.

### WR-05: Unguarded `json.loads` can crash the /methodology page

**File:** `pages/01_methodology.py:183` and `:213`
**Issue:** The eval Surface-2 read (lines 108-114) is correctly guarded with
`.is_file()` + try/except, but the sibling `panel_sanity.json` (line 183) and `card_data.json`
(line 213) reads are NOT. A corrupt/partial JSON in either raises inside the top-level page
body, crashing the entire /methodology page — which now co-hosts the eval metrics surface. This
is inconsistent with the defensive posture used everywhere else in the phase.
**Fix:** Wrap both reads in the same `try/except Exception` used for `_EVAL_SUMMARY_PATH`,
falling back to the honest "not generated yet" note on parse failure.

### WR-06: `run_rag_eval` does not isolate per-question agent crashes

**File:** `scripts/run_eval.py:427`
**Issue:** `final_state = invoke_fn({...}, question)` is called without a try/except, so a
single transient failure in `_retrieval_only_invoke` (live Qdrant/rerank) or
`invoke_with_tracing` aborts the whole run and discards all previously scored questions. Both
`compute_numeric_faithfulness` (722-728) and legacy `run_eval` (150-157) wrap the invoke in
try/except; the first-class runner is the odd one out.
**Fix:** Wrap the invoke in try/except and record a per-question failure row (as the numeric
track does) so one crash does not lose the entire eval pass.

### IN-05: `_ragas_faithfulness` docstring contradicts its behavior

**File:** `scripts/run_eval.py:86` vs `:101`
**Issue:** The docstring says "Returns 0.0 on error," but the code returns `-1.0` (the correct
"not measured" sentinel). The code is right; the docstring is wrong and, given the sentinel's
honesty significance, actively misleading.
**Fix:** Correct the docstring to "-1.0 (not measured) on error."

### IN-06: `_attach_judge_flag` scores an orphan trace, not the run trace

**File:** `scripts/run_eval.py:356-365`
**Issue:** The `judge_flag` failure-mode score is attached to a freshly created
`lf.trace(...)` rather than to the run's enriched trace from `invoke_with_tracing`. In Langfuse
the judge flag is therefore disconnected from the run it describes, degrading the failure-mode
view. (Documented as a limitation, but worth a follow-up.)
**Fix:** Thread the run's trace id into the runner and score that trace, or attach the judge
score inside the same emit path that created the run trace.

### IN-07: Report-link href is HTML-escaped but not scheme-validated

**File:** `ui/eval_inline.py:121-126`
**Issue:** `href = html.escape(str(report), quote=True)` neutralizes quotes/angle-brackets but
not a `javascript:` / `data:` scheme. The `report` value comes from a repo-committed artifact
written by the runner (always a relative `.md` path), and Streamlit's markdown sanitizer
further mitigates, so exploitation is not realistic — but defense-in-depth is cheap.
**Fix:** Validate that `report` is a relative path / `http(s)`-or-relative before emitting the
anchor; otherwise omit the link.

### IN-08: Inline surface bypasses the schema on read

**File:** `ui/eval_inline.py:95`, `:75-77`
**Issue:** `render_eval_inline` reads raw `json.loads` output rather than validating via
`EvalSummary`, so a malformed committed `recall_at_10 = -1` would render as `-1.00` through
`_eval_num` (only faithfulness has the `-1 → "not measured"` special-case). The runner always
writes a schema-valid file, so this is latent, but it means the UI trusts the file's shape.
**Fix:** Optionally `EvalSummary.model_validate_json` at read time (falling back to the muted
empty state on ValidationError) so the render can never surface an out-of-band number.
