<decisions>
## Implementation Decisions

*(Requirements + visual design are locked upstream. These are the implementation-HOW decisions captured in discussion, 2026-08-01.)*

### README shape & depth (OPS-03b)
- **D-01:** README uses a **hybrid shape** — a scannable top (recruiter hook + headline metrics + architecture diagram) readable in ~30 seconds, then deeper sections below (methodology narrative, evals, honest limitations), ending with links to `/methodology`, the committed dashboard, the model card, and `/failures`. Serves both the skimming recruiter and the DS reviewer who wants rigor; matches the project's "rigor visible, not buried" ethos.
- **D-02:** The README's architecture diagram is a **Mermaid fenced code block** (GitHub renders it natively) — text-based, zero external asset, honesty-invariant, and maintainable. It must depict the REAL pipeline (PyMuPDF + pdfplumber → bge-m3 → Qdrant hybrid → bge-reranker → LangGraph agent → Instructor → XGBoost + MAPIE → cited answer; **NOT Docling**). This is the README's render target for the pipeline; the in-app `/methodology` diagram stays the approved UI-SPEC **C1** HTML/CSS hero, and the committed dashboard uses inline HTML — three render targets, one real pipeline.

### Committed HTML eval dashboard (OPS-03a)
- **D-03:** The dashboard is **sectioned by surface** — three sections: **RAG** (recall@k, citation, faithfulness rendered verbatim as "not measured"), **Extraction** (F1), and **Forecast** (conformal coverage + the calibration plot) — with the honest **Swiggy-only per-IPO caveat inline**. Mirrors the eval harness's own structure and reads as more rigorous. Still one self-contained HTML file (inline CSS + inlined plot images, zero external/CDN URLs) per SPEC/UI-SPEC C3.

### App screenshots
- **D-04:** **No app screenshots this phase.** 6.2 surfaces stay entirely text/metrics-based; the live UI ships with the Phase 6.3 public deploy (OPS-02). This keeps 6.2 fully render-only/demo-safe with no headless-capture tooling to build or keep current. (See Deferred Ideas.)

### Claude's Discretion
- **Failure gallery count & ref rigor (FAILGAL-01):** Not discussed — left to the planner/executor, anchored on the brainstorm design doc's candidate list of ~10 real failures. Guidance: target ≥10 (ideally 12–15), balanced so every top-level `surface` ∈ {rag, extraction, forecast} appears ≥1×; prefer citing a verifiable `refs` path (eval report / commit) per entry to harden the honesty invariant, but this is not a hard gate beyond the SPEC's schema+count test.
- Standard implementation details (file layout beyond SPEC's named paths, test structure, Mermaid node phrasing, dashboard section ordering) are the planner's/executor's call, consistent with the locked docs.
