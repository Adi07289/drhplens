# Phase 6.2: Portfolio Surfaces — Specification

**Created:** 2026-08-01
**Ambiguity score:** 0.12 (gate: ≤ 0.20)
**Requirements:** 4 locked

## Goal

Turn the committed 6.1 eval harness into three recruiter-facing surfaces — a browseable
`/failures` gallery, a systems-breadth recruiter landing on `/methodology`, and a
committed off-app HTML eval dashboard + portfolio README — all render-only and
honesty-invariant, so a hiring manager can understand and trust the system without running it.

## Background

The eval harness (Phase 6.1) is on `main`: `eval/reports/eval_summary.json`, dated eval
reports, honest inline eval figures on IPO pages, the `/methodology` page (methodology
writeup + eval rows + model card + gates), and the METHOD-01 "Show your work" pane
(EVAL-04, already delivered). Phase 5 committed calibration/PIT/SHAP plots + a model card
(forecaster does not beat baselines). What does NOT exist: a `/failures` page or any
committed failure data file (`grep` finds none in `eval/`); a recruiter-oriented hero /
architecture diagram on `/methodology`; a committed off-app HTML eval dashboard; and a
portfolio-grade README. The render-only pattern (`.is_file()` + try/except, AST-import
isolation test) from `ui/eval_inline.py` and the Deep-Slate design system are the reuse base.
Full design: `docs/superpowers/specs/2026-08-01-6.2-portfolio-surfaces-design.md`.

## Requirements

1. **FAILGAL-01 — `/failures` gallery**: A browseable failures page renders ≥10 real,
   honestly-labelled failures from a committed data file with no live calls.
   - Current: No `/failures` page, no `ui/failures.py`, no `eval/failures/failures.yaml`. A
     stale "failure gallery" is referenced in copy but not built.
   - Target: `pages/04_failures.py` (URL `/failures`) + `ui/failures.py::render_failures()`
     read a committed `eval/failures/failures.yaml` (≥10 entries; every `surface` ∈
     {rag, extraction, forecast} appears ≥1×; each entry has id, surface, category, query,
     expected, actual, non-empty postmortem, status ∈ {open, mitigated}, refs) and render it
     read-only, HTML-escaped, with no LLM/agent/live-service import.
   - Acceptance: A schema test asserts ≥10 entries, all three surfaces present, and every
     entry has a non-empty postmortem + valid status; an AST-import-isolation test pins
     `ui/failures.py` to an allowlist (yaml/json/pathlib/html/streamlit); a render test
     produces the gallery from the committed file without error and with no live call.

2. **LAND-01 — `/methodology` recruiter landing extension**: `/methodology` opens with a
   systems-breadth hero (accurate architecture diagram) and links the model card,
   `/failures`, and an honest per-IPO eval summary — extending, not replacing, the page.
   - Current: `/methodology` starts at the Evaluation section; no hero, no architecture
     diagram, no `/failures` link, no per-IPO eval summary.
   - Target: A new top hero on `pages/01_methodology.py` — headline + an architecture diagram
     of the REAL pipeline (PyMuPDF+pdfplumber page-anchored parse → bge-m3 → Qdrant hybrid →
     bge-reranker → LangGraph agent → Instructor extract → XGBoost+MAPIE → cited answer; NOT
     Docling) — followed by the existing evidence, plus a prominent `/failures` link, an
     honest per-IPO eval summary ("1 IPO with a real gold set — Swiggy; others show the
     system-level figure"), and a live-demo link placeholder.
   - Acceptance: A render test confirms the hero section renders, the architecture diagram
     names the real components (asserts "PyMuPDF"/"Qdrant"/"LangGraph"/"MAPIE" present and
     "Docling" absent), a `/failures` link is present, and the per-IPO summary shows only
     Swiggy (no fabricated per-IPO numbers). The `/methodology` URL is unchanged.

3. **OPS-03a — committed HTML eval dashboard**: A self-contained HTML eval dashboard is
   generated and committed, rendering the eval numbers off-app.
   - Current: No `eval/dashboards/` dir; eval numbers only viewable in-app or as raw
     markdown/JSON.
   - Target: `scripts/build_eval_dashboard.py` writes `eval/dashboards/eval-dashboard.html`
     — self-contained (inline CSS + inlined images, zero external/CDN URLs) — showing
     recall@k / citation / faithfulness (from `eval_summary.json`), extraction F1, and forecast
     conformal coverage + the calibration plot; the file is committed.
   - Acceptance: A test runs the generator and asserts the output file exists, contains the
     committed `eval_summary.json` numbers (report/surface parity), and references no external
     `http(s)://` asset URL; the committed `eval-dashboard.html` opens standalone in a browser.

4. **OPS-03b — portfolio README**: The repo README is portfolio-grade and cross-links every
   surface.
   - Current: README is not portfolio-oriented; no unified story or links to model card /
     methodology / failures / dashboard.
   - Target: `README.md` presents the story + architecture + evals and links the committed
     dashboard, model card, `/methodology`, `/failures`, and a live-demo placeholder (6.3).
   - Acceptance: README contains a project summary, an architecture description, and working
     repo-relative links to the eval dashboard, the model card, and the failures data/page; a
     link-check confirms the referenced committed files exist.

## Boundaries

**In scope:**
- `/failures` gallery (page + renderer + committed `failures.yaml` with ≥10 real entries).
- `/methodology` recruiter extension (hero + architecture diagram + `/failures` link + honest per-IPO summary).
- Committed self-contained HTML eval dashboard + generator.
- Portfolio README rewrite with cross-links.
- Render tests, schema+count test, AST-isolation test, dashboard-build test.

**Out of scope:**
- **OPS-02 public deploy** (Hugging Face Spaces) — Phase 6.3 (launch gate); the live-demo link is a placeholder here.
- **EVAL-04 "Show your work" pane** — already delivered by METHOD-01 (Phase 3); reused, not rebuilt.
- Live-from-Langfuse failure feed — rejected in brainstorm for demo-safety; failures are curated/committed.
- The four disclosed 6.1 follow-ups (judge calibration, CI gate lane, gold-set span-tightening, WR-03) — gate a production stamp / launch, owned by 6.3.
- The **visual/pixel** design (hero layout, diagram styling, `/failures` card look) — locked in `/gsd-ui-phase` (UI-SPEC), not here.

## Constraints

- **Render-only / demo-safe:** every surface reads only committed artifacts; no LLM/agent/live-service call at render (P19), pinned by AST-import isolation tests (mirrors `ui/eval_inline.py`).
- **Honesty invariant:** neutral presentation, no red/green verdict styling; `open`/`mitigated` shown truthfully; no fabricated per-IPO numbers; the architecture diagram must depict the REAL pipeline (PyMuPDF+pdfplumber, not Docling).
- **Self-contained dashboard:** no external/CDN asset URLs — must render offline from the repo.
- **Reuse, don't rebuild:** extend `pages/01_methodology.py`; reuse `.drhp-*` classes, `ui/copy.py`, and the committed `eval_summary.json` / model card / Phase-5 plots.

## Acceptance Criteria

- [ ] `/failures` renders ≥10 real failures from `eval/failures/failures.yaml`, covering all three surfaces (rag/extraction/forecast), each with category, query, expected-vs-actual, post-mortem, and an honest open/mitigated status — no live calls.
- [ ] `ui/failures.py` passes an AST-import-isolation test (allowlist only).
- [ ] `/methodology` renders a systems-breadth hero + architecture diagram naming the real components (PyMuPDF/Qdrant/LangGraph/MAPIE present, Docling absent), links `/failures`, and shows an honest Swiggy-only per-IPO summary; the `/methodology` URL is unchanged.
- [ ] `eval/dashboards/eval-dashboard.html` is committed, self-contained (no external URLs), and contains the committed `eval_summary.json` numbers.
- [ ] `README.md` is portfolio-grade and links the dashboard, model card, `/methodology`, and `/failures` (all referenced committed files exist).
- [ ] All new render paths are demo-safe (no live service call) and the full offline test suite stays green.
