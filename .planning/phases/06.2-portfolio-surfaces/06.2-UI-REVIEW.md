## Top 3 Priority Fixes

1. **Spacing scale not enforced in the two new component families or the dashboard** — a recruiter who inspects source (a DS-audience is likely to) will see the "no exceptions, 4px scale" claim in `06.2-UI-SPEC.md` contradicted by `app/static/drhplens.css:1796-1801,1899-1902,1903-1906` (chip/pill/connector padding: `3px 10px`, `1px 5px`, `0 6px`) and by nearly the entire `scripts/build_eval_dashboard.py` inline `<style>` (`padding: 64px 24px 96px`, `gap: 12px`, `padding-left: 10px`, `padding: 14px 16px`, `margin: 12px 0 8px` / `6px 0` / `18px 0 6px` / `10px 0 4px`) — concrete fix: replace hardcoded values with the nearest `--drhp-space-*` token in the app CSS, and mirror the token **values** (not just colors) into the dashboard's inline `:root` block so C3 truly "mirrors the same tokens" per the C3 contract, not just the palette.

2. **No-match search reuses the "file not loaded" empty state, giving wrong guidance** — `ui/failures.py:142-154` calls the same `_empty_state()` (`"No failures loaded." / "Run the eval suite to populate eval/failures/failures.yaml."`) whether the committed file is genuinely missing/corrupt *or* the user's search/surface filter matched zero of the 12 loaded entries. A recruiter who types a keyword with no hits is told to go run the eval suite — actively misleading. Concrete fix: add a second, filter-aware empty-state branch (e.g. "No failures match that filter." / "Clear the search or pick a different surface.") gated on whether `entries` was non-empty before filtering.

3. **Failure gallery claims "grouped ... by surface" but renders no visible grouping cue** — `ui/failures.py:156-157` sorts entries by `_SURFACE_ORDER` before the render loop, but no surface-group header/divider is emitted between the rag/extraction/forecast runs, so the 12-card vertical stack reads as one undifferentiated list even though the UI-SPEC's C2 contract explicitly promises grouping for scannability. Concrete fix: emit a `.drhp-fail-group-label` mono heading (reusing the existing lane-label/eyebrow type role) whenever `entry["surface"]` changes from the previous card.

## Detailed Findings

### Pillar 1: Copywriting (4/4)

Evidence of exact contract compliance:

- `pages/01_methodology.py:43-45` — subhead matches verbatim (entities aside: `&nbsp;`/`&mdash;` render to the exact spec text).
- `pages/01_methodology.py:76-77` — `/failures` link + live-demo placeholder `"Live demo — coming with the public deploy (Phase 6.3)."` matches verbatim, rendered via the non-link `.drhp-archhero-demo` class (muted mono, no `href`) — correctly never a clickable stub.
- `pages/01_methodology.py:169-172` — per-IPO note `"1 IPO has a real gold set (Swiggy); others show the system-level figure."` matches verbatim and is gated behind `"swiggy_2024_11" in per_ipo` (`ui/eval_inline.py`-style fabrication guard) — no non-Swiggy figure can print.
- `ui/copy.py:180,183` — `FAILURES_EYEBROW = "FAILURE GALLERY"`, `FAILURES_HEADING = "Where it breaks — and what I did about it"` match verbatim.
- `ui/failures.py:43-44` — empty-state heading/body match the UI-SPEC's Failures-empty-state row verbatim.
- `ui/failures.py:63-73` — `_status_label()` emits exactly `OPEN` / `OPEN · BY DESIGN` / `MITIGATED`, never a raw data string.
- `scripts/build_eval_dashboard.py:53-55` — dashboard title `"DRHPLens — Evaluation Dashboard"` and the Swiggy caveat both match verbatim and are reused identically in the dashboard footer/header.
- `eval/failures/failures.yaml` — all 12 entries are honestly evaluative (e.g. `forecast-does-not-beat-baselines` leads with "It does not... R2 is -0.009 and the P9 release gate FAILS"); none is spun as a win; 6 `open` / 6 `mitigated`, all three surfaces represented (rag×8, forecast×3, extraction×1).

Minor implementation note (not score-affecting): `pages/01_methodology.py:41` and `pages/04_failures.py`/CSS rely on `text-transform: uppercase` (`app/static/drhplens.css:1859-1862`) to turn the mixed-case source string `"Methodology · How it actually works"` into the spec's literal `"METHODOLOGY · HOW IT ACTUALLY WORKS"` at render time — visually correct, but the raw HTML source does not literally contain the spec string (relevant only to a source-diff auditor, not a visual one).

### Pillar 2: Visuals (3/4)

- Strong: the C1 hero has one unambiguous focal point (eyebrow → H1 → subhead → diagram → links, `pages/01_methodology.py:39-81`); the C2 card has clear internal hierarchy (chip row → serif title → two-col grid → hairline-separated postmortem, `ui/failures.py:91-111`); no icon-only buttons exist in the new surfaces (the `✓`/`◆`/`→` glyphs are inline decoration inside labeled text, not standalone controls), so there's no missing-aria-label risk.
- **Gap:** `ui/failures.py:156-157` sorts (`entries = sorted(entries, key=lambda e: _SURFACE_ORDER.get(...))`) but the render loop (`159-165`) never emits a group boundary. The UI-SPEC's C2 contract states "Gallery = vertical stack of cards, grouped/orderable by surface" — the "grouped" half of that promise is not visually realized; a recruiter scrolling the 12-card stack sees rag cards flow directly into the single extraction card and then into forecast cards with zero visual cue distinguishing the transitions.
- **Gap:** the `/failures` page gives no numeric feedback on filter results (e.g. "3 of 12 failures shown") — the only feedback loop is the card count itself shrinking, which is workable but not a strong pattern for a filterable gallery.

### Pillar 3: Color (3/4)

- Honesty invariant fully intact: `grep -niE "color:\s*(red|green)|#e5484d|#d33682|#2ecc71|#3fb950"` returns zero hits across `drhplens.css`, `ui/failures.py`, `pages/01_methodology.py`, `pages/04_failures.py`, `scripts/build_eval_dashboard.py`, and the committed `eval-dashboard.html`.
- `scripts/build_eval_dashboard.py:99-107` mirrors the app's `:root` token **values** exactly (`--bg:#16171A`, `--surface:#1E2024`, `--surface-2:#26282D`, `--border:#33363C`, `--text:#ECECEA`, `--muted:#9A9BA0`, `--accent:#E0A24E`, `--accent-link:#E6AC5C` — byte-identical to `app/static/drhplens.css:22-30`).
- Accent usage in the C2 card is exactly on the spec's reserved list: card left-rule (`app/static/drhplens.css:1789`), Actual-column left-rule (`:1822`), surface chip text via `accent-link` (`:1798`).
- Accent usage in the C1 hero is mostly on-list: connector `→` (`:1904-1906`), single amber-filled output node (`:1896-1897`), eyebrow/caption labels (`:1859-1862`, `:1870-1875`), report link (`:1911-1915`).
- **Finding:** `app/static/drhplens.css:1899-1902` — `.drhp-archhero-chip` (the LangGraph `gate1 · generate · scrub · cite-check` micro-chips) is styled `color: var(--drhp-accent-link)`. The UI-SPEC's "Accent reserved for" list is explicit and enumerated: "eyebrow/lane labels; diagram connectors (→); the single amber-filled ... output node; the failure-card left-rule + surface chip + the Actual-column left-rule; the report/demo links." LangGraph sub-step micro-chips are not on that list. This is a real, citable over-application of the accent color to a fourth diagram element beyond what the contract enumerated — it doesn't break the honesty invariant (still not encoding good/bad) but it is a literal compliance gap in the reserved-element accounting, and it nudges the diagram's accent-to-neutral ratio up from what the spec described.

### Pillar 4: Typography (4/4)

Role-by-role match against the declared table:

- Heading/card-title (17px option): spec 17px/600/1.3 → `app/static/drhplens.css:1812-1815` `.drhp-fail-title` is exactly `font-size:17px; font-weight:600; line-height:1.3`. Exact match.
- Body: spec 14–16px/400/1.55 → `.drhp-archhero-sub` 16px/1.55 (`:1867-1869`), `.drhp-fail-pmbody` 14px/1.6 (`:1840-1842`, line-height 0.05 over spec — trivial).
- Eyebrow/lane/status label: spec 10.5–12px/mono/uppercase/letter-spacing .10–.16em → `.drhp-archhero-eyebrow` 11px/.14em (`:1859-1862`), `.drhp-archhero-lane-label` 10.5px/.12em (`:1881-1884`), `.drhp-fail-chip` 10.5px/.14em (`:1796-1801`), `.drhp-fail-status` 10.5px/.12em (`:1805-1811`), `.drhp-fail-label`/`.drhp-fail-pmlabel` 10.5px/.12em (`:1823-1827`, `:1835-1839`) — all within range.

### Pillar 5: Spacing (2/4)

The `:root` scale itself is declared correctly and matches the contract exactly (`app/static/drhplens.css:37-43`: xs4/sm8/md16/lg24/xl32/2xl48/3xl64). Macro-level layout in the new components correctly uses the tokens: card padding (`.drhp-fail-card` → `var(--drhp-space-md) var(--drhp-space-lg)`, `:1788-1791`), grid/gap spacing (`.drhp-fail-grid` → `var(--drhp-space-md)`, `:1816-1819`), hero-to-diagram spacing (`.drhp-archhero-cap` → `var(--drhp-space-xl) 0 var(--drhp-space-md)`, `:1870-1875`).

However, the UI-SPEC states **"Exceptions: none"** for the spacing scale, and the audit found the following off-scale hardcoded pixel values (none of which resolve to 4/8/16/24/32/48/64):

- `app/static/drhplens.css:1796-1801` `.drhp-fail-chip { padding: 3px 10px; }`
- `app/static/drhplens.css:1805-1811` `.drhp-fail-status { padding: 3px 9px; }`
- `app/static/drhplens.css:1899-1902` `.drhp-archhero-chip { padding: 1px 5px; }`
- `app/static/drhplens.css:1903-1906` `.drhp-archhero-conn { padding: 0 6px; }` (also present in the pre-existing `.drhp-arch-arrow` at `:1752`, so this is a repeated, not new, pattern — but the new C1 component had the opportunity to fix it and didn't)
- `app/static/drhplens.css:1885-1888` `.drhp-archhero-node { padding: 12px 14px; }`
- `scripts/build_eval_dashboard.py:121` `.wrap { padding: 64px 24px 96px; }` — `96px` has no corresponding token (2xl=48, 3xl=64; 96 is neither)
- `scripts/build_eval_dashboard.py:134,141,159,161,167,169,185,193,203` — `margin: 12px 0 8px`, `margin: 6px 0`, `padding-left: 10px`, `margin: 10px 0 4px`, `gap: 12px`, `padding: 8px 0`, `padding: 14px 16px`, `margin: 18px 0 6px`, `margin-top: 6px` — none of these map onto the declared scale.

The C3 dashboard is the worst offender: because it is a hand-authored standalone `<style>` block (not importing the app's CSS), essentially none of its internal padding/margin/gap values reference the 4px scale even though its color tokens are mirrored exactly. The UI-SPEC's C3 contract ("Standalone HTML mirrors the same tokens inline") is satisfied for color but not for spacing — the spec's spacing table doesn't scope itself to "app only," so this reads as a genuine contract gap, not an out-of-scope surface.

### Pillar 6: Experience Design (3/4)

Strengths:
- Render-only posture is exemplary and consistently applied: `ui/failures.py:122-140` guards `.is_file()` + `try/except` around `yaml.safe_load`, degrades to `_empty_state()` on any failure mode (absent file, unreadable, empty list, non-mapping elements) without ever crashing the page.
- `pages/01_methodology.py:204-208,233-237` mirror the same defensive `.is_file()` + `try/except` pattern for `panel_sanity.json` and `card_data.json`, with an explicit comment (`:239-242`) noting a prior CR-01 regression (page-abort on corrupt artifact) was fixed so the rest of the page still renders.
- No destructive actions exist on either surface, correctly matching the UI-SPEC's "No destructive-confirmation copy" note — nothing to confirm.
- The surface + free-text filter (`pages/04_failures.py:50-64`) is fully render-only/in-memory, satisfying the "searchable" requirement without a live call.
- `.streamlit/config.toml` sets `base="dark"` with the exact `--drhp-*` hex values as the Streamlit theme, so the native `st.selectbox`/`st.text_input` filter controls inherit the dark Graphite+Amber palette automatically rather than rendering as default light-theme widgets — a detail that could easily have been missed and wasn't.

Gap:
- `ui/failures.py:122-154` — the SAME `_empty_state()` function (and copy) fires for three distinct situations: (a) the committed YAML file is genuinely missing/corrupt, (b) the file loaded but every element failed the `isinstance(e, dict)` guard, and (c) the file loaded fine but the user's surface/text filter matched zero of the 12 entries. Case (c) is a normal, expected interaction (a recruiter searching for a keyword with no hits), yet it renders "No failures loaded. Run the eval suite to populate `eval/failures/failures.yaml`." — objectively false in that moment (the file **is** loaded; 12 entries **are** committed) and gives the user no path to recover other than guessing to clear the search box. This degrades the "searchable" feature's usability without breaking the page.
